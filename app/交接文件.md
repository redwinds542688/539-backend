## 一、專案是什麼

一個**單一 HTML 檔案**構成的彩券（今彩539、天天樂、六合彩、大樂透）開獎歷史查詢與
分析工具，純前端、沒有後端框架，資料靠 localStorage + IndexedDB 存在瀏覽器裡，
另外會跟一個外部雲端服務同步最新開獎資料。設計給**手機瀏覽器直接開啟本機檔案**
（`content://` URI）使用，不是架設在網頁伺服器上。

- **檔案**：`抓牌.html`（2026-09-07 起的最新版，見【三之三】）；`名揚四海彩卷系統1.html` 為較早的完整版
- **大小**：約 520 KB，1289 行（大部分是被壓縮成單行的 JS/CSS）
- **技術棧**：純 HTML + CSS + Vanilla JS，沒有任何建置工具、沒有 npm、
  沒有框架；唯一的外部依賴是動態載入的 [html2canvas](https://html2canvas.hertzen.com)
  （截圖存檔功能用）

⚠️ **重要**：檔案本身最前面已經內嵌了一大段 JS 註解形式的技術文件
（搜尋 `程式技術文件` 就能找到），裡面完整記錄了架構設計跟修復歷史。
**這份交接文件是外部索引，實際的權威內容以檔案內嵌的那段註解為準**，
兩邊如果有出入，以檔案內的為準（因為那個會隨著程式碼異動即時更新）。

## 二、核心功能模組速覽

### 1. 四招標記系統（抓牌畫面的核心互動）
| 招式 | 觸發方式 | 核心函式 | 資料存放 |
|---|---|---|---|
| 第一招 | 雙擊已開獎號碼格 | `pickCell(td)` | `pickedPaths`（`via:"click"`） |
| 第二招 | 手指橫向滑過整排 | `markCellForDrag`/`unmarkCellForDrag` | `pickedPaths`（`via:"drag"`） |
| 第三招 | 拖曳連接已標記格子 | panels 的第二組 `pointerdown` | `connections` |
| 第四招 | 長按空白格選號 | `openNumPicker(td)` | `numPickedEntries` |

**啟用總開關**：`document.body` 的 `magnifier-mode` class。四招所有互動判斷式
開頭都會檢查這個 class 存不存在。這個 class 只在 `activatePeriodMode()`、
`activateFloatingButtons()`、`showFullPageImage()` 這幾處被正確加上。

**架構鐵律**：所有標記顯示都是透過 `applyMarksToClone()` 統一「清空後依
`pickedPaths` 重繪」。任何新功能如果要疊加標記樣式，**必須**透過
`pickedPaths` 登記，絕對不要直接對 `td` 加 `num-marked`/`num-marked-drag`/
`num-marked-click` 這三個 class，否則會被清空重繪機制打架、互相覆蓋
（這是本次對話發現的重要教訓，來自另一份更早的專案交接文件）。

### 2. 定期十六 / E式 / C式
三者共用同一個進入函式 `togglePeriodMode()` → `activatePeriodMode()`：

- **定期十六**（`period16Btn`）：純放大顯示最近 16~21 期
- **E式**（`clearBtn`，「E式概率」按鈕）：目前程式碼上跟定期十六**完全相同**，
  沒有獨立運算邏輯，只是另一個入口/標籤——**這是一個值得優化/釐清的地方**，
  也許之後要嘛實作真正的 E 式邏輯，要嘛乾脆合併成同一個功能，減少混淆
- **C式**（`broadBtn`）：額外呼叫 `applyCModeAutoFraming()`，疊加「定/差/合」
  分析層，`cModeActive = true`

**C 式的鎖定/解鎖機制**：
- 啟用時：`resetAllFourMoveMarks()` 清空定期十六階段留下的四招痕跡，
  同時一二三四招全數被鎖（各自的處理函式裡都加了 `if(cModeActive)return`）
- 離開時：**統一由 `forceExitCModeIfActive()` 處理**，被多個進入/退出路徑
  （`togglePeriodMode` 退出分支、`closeBtn` 點擊、`activateFloatingButtons()`/
  `showFullPageImage()` 這兩個進入點）共同呼叫，確保任何路徑都會正確解鎖、清空

### 3. 統計表（長按「定」／長按「差」）
兩者共用同一套「九宮拖牌」演算法（`calcNineGridDrag`），抓上下桿往前推
`cModeDingSearchSpan`/`cModeChaSearchSpan` 期，比對候選格子跟 B 錨點列
的九宮拖牌關係，命中就計數。

**唯一差別（過濾方向相反）**：
- 「定」→ `computeCModeDingStatCounts()`：**排除**已標記的格子，
  只對「完全沒被標記」的候選格子做運算
- 「差」→ `computeCModeChaStatCounts()`：**只對**「已經被標記」的格子做運算

判斷「有沒有被標記」統一查詢 `pickedPaths` 陣列。UI 用 `顏色數字表`
（淺灰 `#E5E5E5` → 深紅 `#7A0000` 共9階熱力圖）+ 最高分綠色閃爍動畫。
兩張統計表互斥、拖曳桿時會即時歸零重算。

### 4. 除錯瓢蟲系統（🐞 左下角固定按鈕）
- **輕點**：擷取「按下當下往前推 2 秒內」的事件記錄，存成 `.txt` 下載
- **長按（~0.5秒）**：打開完整記錄檢視器
- `logEvent(tag, detail)` 全域函式，事件寫入記憶體陣列 `bugLog`（上限1500筆），
  同時每 0.5 秒節流寫入 `localStorage`（key: `539app_bugLog`），
  `window.onerror`/`unhandledrejection` 自動記錄 JS 錯誤堆疊
- 瓢蟲在畫面上的位置由 `positionPinOnScreen()` 動態決定，
  **四種完全獨立、互不共用邏輯的判斷分支**（C式／定期十六與E式／抓牌首頁／一般首頁）

### 5. 資料存取
- **存**：手動輸入或雲端同步新增記錄，只寫入 `localStorage`
  （`saveDbToLocalStorage`）+ IndexedDB（`saveDrawRecordToDB`），
  **不會**觸發任何檔案下載（`exportLotteryDatabaseAsFile` 已整個移除）
- **讀**：開機 `boot()` 一開始就 `await loadLotteryLocalDBIntoEmbedded()`，
  確保本機資料在畫面第一次渲染前就套用完成，避免閃爍舊資料。
  內部**兩邊都讀**（localStorage 跟 IndexedDB），用 `_savedAt` 時間戳比新舊，
  永遠留下最新的一筆
- **雲端同步**：`manualUpdateAndMergeData()`（開機執行）+
  `runScheduledCloudChecks()`（每60秒排程，涵蓋四種玩法在特定時段自動抓取），
  依賴外部服務 `hearty-vitality-production-0687.up.railway.app`

### 6. 截圖／存檔／印單
`saveAsImage()` / `saveCleanSheetImage()`，用 html2canvas 擷取畫面輸出 PNG。
**設計決策**：這兩個函式跟 C 式完全脫鉤，不認識 C 式的存在——C 式的覆蓋元素
（紅色參考弧線、拖曳把手）自己用 `MutationObserver` 監看 `recent-only-mode`
class 自動清理（`clearCModeOverlay()`），不需要（也不應該）讓存檔功能反過來
認識 C 式的內部狀態。

## 三、本次對話完整修復紀錄

1. 統計表打開時，標定號碼背景/圓形標記、差合連線弧線、上下桿紅色參考弧線
   被 CSS 強制隱藏 → 移除 `body.c-mode-stat-open` 相關隱藏規則
2. `renderCModeArcLoop()` 內部另外寫死的判斷式會在統計表打開時清空紅色參考弧線
   → 移除該判斷式
3. 存檔用 html2canvas 擷取整頁時，C 式的 `position:fixed` 覆蓋元素會被錯誤
   拉伸到超長截圖上 → 最終方案是讓 C 式自己負責清理，不讓存檔函式認識 C 式
4. **（最關鍵的一個）** 一二三四招在定期十六裡完全沒反應 → 原始檔案從頭到尾
   沒有任何程式碼會把 `body.magnifier-mode` 這個總開關 class **加上**去
   （只有 remove，沒有 add）→ 已在 `activatePeriodMode()` 補上
5. C 式的狀態在某些進入/退出路徑下可能沒有正確解鎖 `cModeActive`，
   導致定期十六裡的第二招被誤鎖 → 新增 `forceExitCModeIfActive()` 統一入口
6. 手動輸入開獎號碼後自動觸發 JSON 資料庫下載通知 → `exportLotteryDatabaseAsFile()`
   整個函式移除，改為只寫入 localStorage/IndexedDB
7. 開機讀取本機資料庫的順序調整為「兩邊都讀、用時間戳比新舊」，
   並把資料載入時機提前到畫面渲染之前
8. 使用者反應「經常無法讀取網頁」（Chrome 的 Aw-Snap 分頁當機畫面）→
   發現每次切換 App 回來都會觸發完整的 `loadData()` 重抓+重畫，
   已加上 60 秒節流（`VISIBILITY_REFRESH_COOLDOWN_MS`），減少資源消耗頻率

## 三之二、2026-08-21 效能優化（Claude Code，含實測數據）

用無頭 Chromium（412×915 手機視窗、6 倍 CPU 節流）實際跑出來的，不是憑程式碼推測。

| 項目 | 改前 | 改後 |
|---|---|---|
| 存一次檔的畫布記憶體瞬時峰值 | 136.3 MB | **100.5 MB** |
| 存檔結束後仍佔用的畫布記憶體 | 136.3 MB（等 GC） | **0 MB**（立即釋放） |
| 「存」和「印」時間接近而重疊時的峰值 | **272.5 MB** | **100.5 MB** |
| C 式靜止 3 秒，弧線層 DOM 變動次數 | 543 次 | **0 次** |
| C 式每幀重繪成本（60 條連線） | 21.4 ms | **5.1 ms** |
| 存檔耗時 | 約 2.6 秒 | 約 2.5 秒 |

實際做的五件事：

1. **存檔流程移除多餘的全尺寸中繼畫布** — 原本要同時擺三張大圖
   （html2canvas 原圖、加留白的複製、A3 紙張），現在直接在 html2canvas
   回傳的畫布上補字，留白改成縮放進紙張時才內縮。
   ⚠️ 重要陷阱：html2canvas 回傳的畫布，其 2D context 內部**還留著
   `scale(6,6)` 的變換矩陣**，重用它之前一定要
   `ctx.setTransform(1,0,0,1,0,0)`，否則字會被放大 36 倍。
2. **畫布用完立刻釋放** — 新增 `releaseCanvasMemory()`，把
   `canvas.width/height` 設 0 直接歸還底層點陣圖，不等 GC。
3. **存檔互斥鎖 `captureBusy`** — 「存」和「印」不會再同時跑。
4. **C 式 rAF 迴圈：沒變就不重畫** — 用「四個錨點 rect + 連線/弧線陣列的
   物件識別」組成 signature，跟上一幀一樣就整段跳過；真的要重畫時改成
   先一次量完所有 rect（純讀）、再用 DocumentFragment 一次掛上（純寫），
   避免讀寫交錯的 layout thrashing。`clearCModeOverlay()` 會作廢 signature。
5. **雲端排程在畫面隱藏時跳過** — 每 60 秒的 `runScheduledCloudChecks()`
   加上 `if(document.hidden) return`。

**輸出結果驗證**：改前改後各跑一次「存」與「印」，輸出的 A3 PNG 逐像素比對，
差異只有 0.109% 且全部集中在最外框線（位移不到 1px），表格內容像素完全相同。

## 三之三、2026-09-07 抓牌版效能優化（Claude Code，含實測數據）

> 從這一版起，最新的程式是 **`app/抓牌.html`**（抓牌版，PWA 名稱「抓牌」，約 1.2 MB）。
> `名揚四海彩卷系統1.html` 是較早的完整版，保留做對照。抓牌版檔案最前面的
> HTML 註解「【抓牌版 修正紀錄】」與 `<script>` 內的「完整技術文件」仍是權威來源，
> 這次的細節記在那裡的第 56 條與【★2026-09-07】段落。

**檢查結果**：11 個 `<script>` 區塊全部通過語法解析；無頭 Chromium（412×915 手機視窗、
有觸控）實際開啟、兩指縮放進全頁、雙擊第一顆進 C 式差數、雙擊第二顆截圖、雙擊「返回」回主頁、
四種玩法分頁切換，全程沒有任何 JS 錯誤；C 式靜止 3 秒 DOM 變動 0 次（上次做的弧線簽名快取仍有效）。

**找到的效能問題**：`applyDesktopScrollerWidth()` 每次呼叫都「先把 `#panels` 的 zoom 重設回 0.59
量自然寬度、再寫回最終 zoom」，兩次 zoom 改動各逼瀏覽器把整份表格（約 1400 格）重新排版一次。
開機時 `buildPanels` 後的 rAF 與 `runHomeInitialReset` 的 rAF 各叫一次，切回 App（visibilitychange）
與 pageshow 也會再叫——第二次以後全是重複計算。另外 `buildPanels` 後的 rAF 先讀 `offsetWidth`
再套 zoom，等於先用 zoom=1 把剛建好的表格白排一次。

**做的三件事**（畫面像素與改前完全相同，改前改後截圖逐像素比對 12 張全部 IDENTICAL）：

1. `applyDesktopScrollerWidth` 加「輸入簽名」快取 `__adswSig()`：表格建立序號
   （`window.__panelsBuildSeq`，`buildPanels` 每次 +1）、玩法、body class、螢幕尺寸、上次量到的視窗寬
   （用 `matchMedia("(width: Npx)")` 判斷，刻意不讀 `innerWidth`/`visualViewport.width`，這兩個在 Chrome
   會強制排版）、頁面倍率、桌機斷點，再加上這支函式自己寫的行內樣式。簽名沒變就直接 return；
   行內樣式也算進簽名，所以任何路徑把 zoom 清成 `""` 都會自動重算，不會用到過期結果。
2. `buildPanels` 後的 rAF（`syncHeroDateWidth`）改成先 `applyDesktopScrollerWidth()` 再讀 `offsetWidth`。
3. 開機末尾的 `syncLotteryLocalDB()`（四種玩法約 1100 筆全量 put 進 IndexedDB，主執行緒約 60ms）
   改用 `requestIdleCallback`（最晚 4 秒），不再跟開機後第一次操作搶主執行緒。

| 項目 | 改前 | 改後 |
|---|---|---|
| 開機時 JS 觸發的整頁強制排版（1 倍 CPU） | 3 次／221 ms | **1 次／122 ms** |
| 開機長任務總時長（1 倍 CPU） | 406 ms | **216 ms** |
| 開機長任務總時長（6 倍 CPU 節流） | 3725 ms | **2348 ms** |
| 切回 App 路徑 `runHomeInitialReset` 連跑 5 次：`applyDesktopScrollerWidth` | 240 ms（5 次都重算） | **0.7 ms**（只第 1 次算） |
| 同上：`syncHomeFixedTopHeight` | 232 ms | **0.2 ms** |

**看過但沒動的**：`loadLotteryLocalDBIntoEmbedded` 約 30ms 幾乎都是等 IndexedDB 回應，主執行緒只有
3ms；截圖（html2canvas）約 530ms 長任務是函式庫本身；四份技術文件註解約 200KB 對解析時間影響極小
（EvaluateScript 合計約 60ms），依專案規則保留在檔案內。

## 三之四、2026-09-07 下桿拖到底＝回溯（第 57 條）

使用者需求：下桿範圍 14～17。下桿在 14 再往上拖，要出現「捲動鍵裡手指下滑」的效果
（原第 16 期變空白、15 變 16、14 變 15…）；下桿在 17 再往下拖則反向收回。

做法：完全沿用捲動區回溯那套（`cModeScrollOffset`／`applyCModeScrollOffset`／`tr.c-scroll-blanked`），
新增 `cModeDragScrollAtLimit(period)` 掛在下桿 touchmove 的 C 式分支尾端：k＝拖曳開始時的回溯值＋手指超出 14 上方的列數
－超出 17 下方的列數（對稱：在 14 上方往回下移立刻 k−1、在 17 下方往回上移立刻 k+1；k 到上下限多拖的不算，橡皮筋）。
桿子位置不動、動的是視窗內容；放手後照常重搜。
退出 C 式時 k 歸零（原本只在捲動鍵開著時歸零）、表格重畫後重套回溯的條件改成「C 式啟用且 k>0」。
只在 C 式生效，E 式等距不變。細節與驗證結果在檔內技術文件【★2026-09-07：下桿拖到底還繼續拖＝回溯】；2026-09-08 改為平滑版，見【三之五】。

## 三之六、2026-09-08 「16+4 先滿屏再縮回」的根本原因（第 65 條）

使用者回報 C 式裡 16+4 常常先以滿屏顯示、再縮回壓縮後的樣子。用無頭 Chromium 每幀偵測「表格可見但沒有 scaleX 壓縮」，
重現出：C 式裡只要表格重建（切回 App 的 `loadData()`、GitHub 同步、手動輸入新增一筆）就有 6～7 幀（約 100～220ms）滿屏，
而且時序紀錄裡遮罩 `c-ding-entering` 從頭到尾沒有掛上。

**根本原因**：`cModeActive`、`recentOnly`、`applyCCompactLayout` 都是 `setupImageView()` 閉包內的變數／函式，
而 `buildPanels()` 與 `boot()` 是全域函式讀不到它們。`buildPanels` 開頭 2026-09-05 加的遮罩判斷
`typeof cModeActive!=="undefined"&&cModeActive` 永遠是 false，遮罩從加上去那天起一次都沒生效；同一段裡的
「重建後 rAF×2 重新壓縮」也從未執行過（實際一直是 `__reapplyMagnifierState()` 在做）。另外 `boot()` 的
visibilitychange 處理直接寫 `if(cModeActive)` 沒有 typeof 保護，切回 App 超過 1 分鐘會丟 ReferenceError，
後面的 `loadData()` 與 GitHub 同步整個不執行。第 8 條其實早就踩過同一個坑並改用 body class，但這幾處漏改。

**修法**：全部改用 body class 判斷（`c-mode-active`、`magnifier-mode`、`recent-only-mode`）。修後時序：
表格重建 25ms 時 mask ON → 壓縮 223ms → 247ms mask OFF；所有路徑「可見且未壓縮」幀數 0；切回 App 超過 1 分鐘
的路徑正常執行 loadData 且無錯誤。

**給接手者的鐵律**：`cModeActive`／`recentOnly`／`cModeAPeriod`／`applyCCompactLayout` 這類閉包變數，
在 `buildPanels`、`loadData`、`boot`、`manualUpsertDrawRecord` 等全域函式裡一律讀不到；要判斷模式請用 body class，
`typeof x!=="undefined"` 這種寫法只會讓錯誤安靜地變成「永遠不執行」。

## 四、已知問題／建議優化方向

這些是目前還沒解決、或值得進一步深挖的地方，特別適合交給 Claude Code
（因為需要實際跑程式碼/量測效能，這邊聊天環境做不到）：

### 🟠 原「高優先：偶發性瀏覽器分頁當機」— 已找到主因並處理，待真機回報確認

**實測結論：不是慢性記憶體洩漏，是存檔當下的瞬間爆量。**

已經量過並**排除**的懷疑項目（不用再花時間查）：
- `buildPanels()` 連續呼叫 40 次、切換玩法 20 次、visibilitychange 30 次之後，
  JS heap（1.4→1.5MB）、DOM 節點數、事件監聽器數量都沒有成長
  → 沒有 detached DOM 累積，也沒有監聽器堆積
- 切回 App 的 `loadData()` 節流確認有生效（30 次切換只有第 1 次真的重載）
- 開機時間在 6 倍 CPU 節流下約 550ms，不是當機主因

**真正找到的原因**：按一次「存」或「印」，畫布記憶體瞬間衝到 136MB 且不會馬上
釋放；如果「存」和「印」時間接近而重疊，峰值達 **272MB** —— 手機 Chrome 的
renderer 到這個量級就會被系統直接砍掉，畫面就是使用者看到的「糟糕！」。
已依【三之二】的 1~3 項處理，峰值降到 100.5MB 且結束後歸零。

**還需要使用者回報**：這是在無頭 Chromium 上量到的，真機的可用記憶體上限
會因手機型號、同時開的分頁數而不同。請實際用一段時間，看「糟糕！」還會不會出現。
如果還會，下一步建議往這兩個方向查：
- `html2canvas` 的 `scale:6`（實測產出 2436×3666）**不是**可以省的地方：
  A3 輸出 3508×4961 需要約 8.6 倍才滿版、A4 輸出 2480×3508 需要約 6.1 倍，
  也就是目前的 6 倍已經略低於紙張解析度。調高只會多吃記憶體、調低會糊掉，
  維持 6 是對的。
- html2canvas 擷取時會把整個 DOM 複製到一個隱藏 iframe（實測 DOM 節點數
  會從 10,268 短暫衝到 15,139），這部分是函式庫內部行為，要省只能換方案

### 🟡 中優先：E式沒有獨立邏輯
「E式概率」按鈕目前跟「定期十六」做的事完全一樣（都是呼叫 `togglePeriodMode`），
沒有實作任何專屬的 E 式運算。需要跟使用者確認：
- E 式原本應該是什麼功能？（可能要問清楚需求）
- 還是乾脆把這個按鈕拿掉/合併，減少介面混淆？

### 🟡 中優先：單一巨型檔案的可維護性
所有邏輯都塞在一個 520KB 的 HTML 檔案裡，JS 大多被壓縮成單行，
用文字比對(str_replace)方式修改風險較高（容易因為字串不完全匹配而失敗，
或改錯地方）。適合的優化方向：
- 拆分成多個邏輯模組檔案（但要注意：使用者是直接用手機瀏覽器開
  `content://` 本機檔案，`<script src>`/`fetch` 載入外部檔案在這種環境
  下大機率會被瀏覽器安全機制擋掉——**拆分前務必先確認部署方式會不會改變**，
  如果堅持要維持「單檔開啟」的使用模式，建議用建置工具（如 esbuild/rollup）
  在開發階段拆分成多檔案方便維護，**最終仍打包輸出成單一 HTML 檔案**給使用者
- 加上基本的自動化測試（至少涵蓋 `pathKey`/`normalizedNum`/
  `calcNineGridDrag`/`mergeRecordInto` 這類純函式邏輯）

### 🟢 低優先：程式碼風格
目前 JS 大量使用中文變數/函式名稱（例如 `顏色數字表`、`今彩539九宮拖牌`），
混合英文命名。這是刻意的選擇（方便中文使用者維護），優化時**不建議**
改成全英文命名，除非使用者主動要求。
