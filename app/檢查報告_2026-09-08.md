### 2.2 開機後 GitHub 同步（問題一）

開機後 8 秒內的觀察：

| 指標 | 數值 |
|---|---|
| 主執行緒佔用 | **7.2 秒**（其中版面重排 4.27 秒） |
| 版面重排次數 | **88 次** |
| `buildPanels()` 表格重建次數 | **21 次** |
| localStorage 整包寫入次數 | **51 次** |
| DOM 節點瞬間峰值 | **69,502**（穩定後 5,070） |
| 最長單一長任務 | 5,233 ms |

CPU 分析器熱點（總時間）：`syncHeroDateWidth` 5,330 ms、`applyDesktopScrollerWidth` 2,810 ms、
`syncCrawlerDataFromGithub` → `manualUpsertDrawRecord` 1,334 ms、`buildPanels` 1,274 ms。

**根因**：`syncCrawlerDataFromGithub()` 對每一筆新資料呼叫 `manualUpsertDrawRecord()`，後者每筆都
`saveDbToLocalStorage()`（整包序列化）＋ `buildPanels()`（整張約 1,000 格表格重建）。新裝檔案的內嵌資料
（539 到 2026-08-17）與雲端最新（2026-09-07）相差 13 筆，四種玩法合計 50 筆，因此重建 13 次、寫入 51 次。
每次重建後第一個讀取版面的函式（`syncHeroDateWidth`）承擔整張表的強制重排成本。

### 2.5 E式等距靜止時每幀重畫（問題二）

延長觀察至靜止 5 秒：主執行緒 **1.20 秒**、版面重排 **600 次**（每秒約 120 次）。
CPU 分析器熱點：`renderCModeArcLoop` → `renderEModeArcFrame` 701 ms、`renderCModeDingAutoDragLines` 430 ms、
`getBoundingClientRect` 308 ms、`querySelectorAll` 182 ms。

**根因**：`renderEModeArcFrame()` 每一幀無條件重畫三桿弧線、拖曳鍵定位、標定連線（`svg.innerHTML=""` 後重建）。
寫入 DOM 之後下一幀再量 `getBoundingClientRect` 就強制重排，形成每幀「寫→讀」循環。C式雙桿迴圈在 2026-08-21
已加 `cModeArcSig` 簽章快取，E式三桿函式為 2026-09-03 另寫，沒有跟上。

### 2.6 量到但未修改

- 雙擊「抓」進抓牌首頁時 `fitFullSheetToFrame()` 執行兩次（第二次為原設計的 `setTimeout` 保險），
  每次約一次全表強制重排（4 倍節流 320 ms，實機約 0.16 秒），一次性成本，未動。
- C式模式靜止時 rAF 迴圈每幀執行 `syncLeftBlankFrameBottom()`（純讀取，無重排），3 秒 0.14 秒，可接受。

## 三、修改內容

### 3.1 GitHub 同步改批次寫入

- 新增 `runUpsertBatch(fn)`、`flushUpsertBatch()`，變數 `upsertBatchDepth`、`upsertBatchPending`。
- `manualUpsertDrawRecord()` 在批次中只更新記憶體陣列、寫 IndexedDB、清除過期選號，localStorage 存檔與
  表格重建登記後延到批次結束，每個玩法各做一次。
- `syncCrawlerDataFromGithub()` 的套用迴圈整個包在 `runUpsertBatch` 裡。
- 手動輸入單筆（深度為 0）走原路徑，行為不變。

### 3.2 E式等距 rAF 迴圈加簽章快取

- 新增 `eModeArcSig`（`{sig, pairs, arcs, specs}`），宣告於 `cModeArcSig` 旁。
- 簽章由上／中／下桿六個錨點 rect、視窗寬度、三組連線資料的身分與筆數組成；相同且三個覆蓋元素仍存在就整段跳過。
- `clearCModeOverlay()` 一併作廢簽章。

### 3.3 文件同步更新

- 檔案頂部技術文件新增【★2026-09-08：效能優化二】，主程式內嵌文件新增【十一】，「最後更新」日期改為 2026-09-08。
- `交接文件.md` 新增「三之三」章節、更新檔名、檔案大小與 E式相關的已知問題描述。

## 五、後續建議（未在本次處理）

1. **實機回報**：以上為無頭 Chromium 數據，建議在實際手機上觀察新裝檔案第一次開機是否更順、E式等距畫面停留時發熱／耗電是否改善。
2. **抓牌首頁進入的雙重版面適配**：若之後覺得雙擊「抓」仍有頓挫感，可評估把第二次 `fitFullSheetToFrame()` 改成「第一次結果無效時才重跑」。
3. **E式概率**：仍與「定期十六」完全相同，沒有獨立邏輯，需與使用者確認要實作、合併或移除。
4. **架構鐵律（已寫入內嵌文件）**：
   - 任何一次套用多筆資料的新功能都要包在 `runUpsertBatch` 裡。
   - C式／E式的連線、弧線資料要「換新陣列」而不是 `push` 到舊陣列，否則簽章快取看不出變化不會重畫。
