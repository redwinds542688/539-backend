## 一、專案基本資料

- **單一 HTML 檔案**：`539app.html`（約 6400+ 行，內含全部 HTML/CSS/JS，沒有外部檔案依賴，除了雲端資料庫 API 跟兩個獨立後端服務）
- **執行環境**：手機（Android）原生瀏覽器直接開啟本機檔案（`content://` 路徑），**不是**部署在網頁伺服器上
- **這帶來的限制**：
  - 無法用一般網頁的方式做版本控制/熱更新，每次修改都要重新產生整個檔案給使用者手動替換
  - Android System WebView 的某些 API 行為跟桌面瀏覽器不一致（詳見下面「已知環境限制」）
  - 沒有後端伺服器渲染，所有邏輯都在前端 JS 執行

## 五、已知環境限制（Android WebView 特有的坑）

### 5.1 `fetch()` + `AbortController` 的 DataCloneError
- 特定版本的 Android System WebView，`fetch()` 搭配 `AbortController.signal` 會誤拋 `DataCloneError`
- 修法：改用 `Promise.race([fetchPromise, timeoutPromise])` 做逾時控制，不傳 `signal` 給 `fetch()`

### 5.2 `overflow:hidden` 會裁掉任何超出格子邊界的內容
- `table.road td{ overflow:hidden; }` 是全域基礎規則，任何用 `position:absolute` + 位移把內容推出格子邊界的嘗試，都會被完全裁掉、變成看不見（不是位置偏差，是根本沒畫出來）
- 這個限制導致這次會話花了很多輪反覆調整第一招圓形補畫格線的位置/位移量，**教訓**：要讓元素的視覺效果超出父層邊界時，一定要先確認父層有沒有 `overflow:hidden`，不然位移只會造成「消失」而不是「移動」
- 如果真的需要讓某個元素的效果超出格子邊界，要嘛「只針對那個特定選擇器」加 `overflow:visible`（範圍越小越安全），不要動全域的 `table.road td` 基礎規則

### 5.3 CSS 繪製順序：`z-index:0` 的定位子元素會蓋住父層自己的邊框
- 瀏覽器畫一個元素的順序是「先畫這個元素自己的背景/邊框，再畫它裡面 `position:absolute`、`z-index:0` 的子元素」
- 第一招的圓形（`::before`，`z-index:0`）天生就會蓋住 `td` 自己的原生 `border-bottom`/`border-right`
- 修法：用另一個偽元素（`::after`）配上更高的 `z-index`，重新畫一次跟原生邊框一樣的線（用 `box-shadow` 的 `inset` 寫法，因為 inset box-shadow 天生完全包在元素自己的 box 裡面，不會被 `overflow:hidden` 裁到，是這次踩過坑之後找到的最穩健做法）

### 5.4 `html2canvas` 對某些 CSS 特性在極端縮放下算不準
- 「定期十六」模式套用了極端、非等比例的 `transform:scale()`（例如 `scale(4.558, 3.9)`），`html2canvas` 在這種「transform 疊 transform」又是非等比例縮放的情況下，對 `outline`、`box-shadow`、偽元素的 `transform:translate()` 置中這些 CSS 特性算不準，會產生破圖
- 修法模式（重複用了三次，是這個 App 處理 html2canvas 限制的標準手法）：
  1. 加一條 `body.capturing-plain ...{ ...none !important; }` 隱藏原生的問題渲染
  2. 改由 JS 在 `saveAsImage()` 裡用 Canvas 2D 手動補畫，量 `getBoundingClientRect()` 取得真實螢幕座標，換算成畫布座標

### 5.5 Canvas 2D 的 `textBaseline:"middle"` 對數字字符置中會偏高
- 因為是用整個字體（含英文字母上下伸出部分）的中線去算，不是數字本身視覺中心，需要手動加一個經驗值的向下修正

### 10.2 header.top（四顆彩券按鍵）固定定位系統
使用者要求抓牌系統裡上滑開獎單時，四顆彩券名稱按鍵要固定在畫面最上方。這個功能踩了好幾層坑，完整解法分散在多個地方：

1. **CSS `position:fixed` 對 transform 祖先失效**：`header.top` 的父層 `#page-zoom-wrap` 會被 JS 動態套用 `transform:scale()`（兩指縮放用），CSS 規則是「祖先元素只要有 `transform`，子元素的 `position:fixed` 就會失效，變成只是相對於那個祖先固定」。修法：進入抓牌模式時用 JS 把 `header.top` 從 `#page-zoom-wrap` 搬到 `#header-top-bg-wrap`（見下一點），離開時搬回原位（用 `#header-top-anchor` 這個空佔位元素標記插入點）。
2. **兩側縫隙透出開獎單**：`header.top` 自己用 `margin:0 14px`（不是 padding）做左右間距，margin 是「外框本身縮進去」，兩側各留 14px 沒有背景覆蓋。修法：新增 `#header-top-bg-wrap` 這個外層滿版背景包裹層，本身沒有 margin、真正滿版整個螢幕寬度，`header.top` 維持原本的 margin 邏輯放在裡面。
3. **`#page-zoom-wrap` 需要補上方留白**：`header.top` 變成 fixed 之後脫離版面流，後面的開獎單內容會被蓋住，補上 `body.magnifier-mode #page-zoom-wrap{ padding-top:80px; }`。
4. **「定期十六」不能受影響**：定期十六本身 header.top 就是 `display:none` 整個隱藏，不需要留白，加了 `body.recent-only-mode #page-zoom-wrap{ padding-top:0 !important; }` 排除。

### 10.3 九宮鍵工具列（`.hint-bar`/`#img-hint`）背景延伸
- `applyImgHintBarConnect()` 函式原本一段「延伸寬度到跟 `#panels` 實際右邊界切齊」的註解一直沒有對應的程式碼（舊版遺留的過時說明），這次補上了缺失的延伸邏輯。
- 同樣因為 `.hero` 用 margin 做間距造成兩側縫隙，新增 `#hint-bar-bg-wrap` 背景包裹層，做法跟 header-top-bg-wrap 相同套路。
- **「定期十六」排除**：`#hint-bar-bg-wrap`、`#header-top-bg-wrap` 都要加 `body.magnifier-mode.recent-only-mode` 的排除規則（`display:none`），不然背景層在定期十六裡不會跟著實際內容一起隱藏，留下一塊空白色塊。這是這次真正抓出「定期十六中間空白」bug 的根本原因。
- **九宮鍵框不能跟著兩指縮放放大**：`.img-hint` 的寬高原本直接複製 `.hero` 的 `getBoundingClientRect()`，但 `.hero` 在 `#page-zoom-wrap` 裡面會被 `pageZoom` 這個 transform 放大，量到的數字已經是放大過的。修法：最後設定 CSS 寬高之前，除以目前的 `pageZoom` 倍率換算回原始尺寸，位置（left/top）不受影響。

### 10.4 兩指縮放自動觸發「全頁模式」（`pinch-fullscreen-mode`）
新功能：抓牌系統裡只要偵測到兩指縮放動作，立刻進入全頁模式——隱藏四顆彩券按鍵、九宮鍵工具列，只留開獎單本身+左上角一顆 ✕ 鍵（`#pinch-fullscreen-close-btn`），連點兩下 ✕ 鍵恢復成剛進入抓牌系統的初始畫面。

實作重點（都在 `touchmove` 的 pinch handler 裡）：
- 用 `!document.body.classList.contains("pinch-fullscreen-mode")` 判斷「是不是第一次進入全頁模式的這一格畫面」，只有這一格強制 `window.scrollTo` 到最上面，之後每個 frame 恢復正常的手指錨點捲動邏輯（兩者互相衝突，只在轉換瞬間用捲到最上面優先）。
- `.hero` 在全頁模式要改成 `display:none`（不是 `visibility:hidden`），因為 visibility:hidden 還是會保留版面空間，造成頂端空白。
- `#page-zoom-wrap` 的 `margin-left:-1%`（首頁偏移用）在全頁模式要蓋回 0，否則左右留白不對稱——JS 層面直接設 inline style 當保險，不只靠 CSS。
- 水平捲動要 clamp 在內容邊界內：新增一個通用的 `scroll` 事件監聽器（不是只在 pinch handler 裡處理，因為單指滑動是原生捲動、不會經過 pinch handler），全頁模式下即時修正 `scrollX` 不超出 `#page-zoom-wrap` 實際寬度。
- **「定期十六」必須完全排除**：在 pinch handler 最前面加 `if(document.body.classList.contains("recent-only-mode")) return;`，直接跳過整段全頁模式邏輯；`applyRecentOnly()` 進入定期十六時也要順便清掉可能殘留的 `pinch-fullscreen-mode` class（例如使用者先觸發過全頁模式又沒有正常從 ✕ 鍵退出）。

## 十二、程式碼裡的註解慣例

這個檔案累積了大量中文行內註解，記錄「使用者要求了什麼」「為什麼這樣改」「踩過什麼坑」，**這是刻意的**，方便之後回溯每一段邏輯的來龍去脈。建議接手後繼續維持這個習慣：每次改動都寫清楚「使用者的原始要求」+「技術上為什麼這樣做」，不要只寫「what」不寫「why」。
